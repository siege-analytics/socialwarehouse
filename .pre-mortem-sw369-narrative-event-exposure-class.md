## Pre-mortem: NarrativeEvent + EventParticipant.exposure_class (SW#369)

Risks considered before and during implementation, each with severity, likelihood, and mitigation.

- **Tiger 1: whitespace-only `sourcing_note` silently defeats the `incidental_private` guardrail**
  **Severity:** HIGH
  **Likelihood:** was realized -- confirmed by hostile review before merge, not hypothetical.
  **Mitigation:** DB `CheckConstraint` now uses `sourcing_note__regex=r"\S"` instead of a literal empty-string check, closing the gap on the real write path (`.objects.create()`/`.update()`), which never calls `clean()`. Covered by `test_incidental_private_with_whitespace_only_sourcing_note_rejected_on_real_write_path`.

- **Tiger 2: `duration_mode="bounded"` with no window bound set is a silent no-op state**
  **Severity:** MEDIUM
  **Likelihood:** was realized -- confirmed by hostile review; the shipped `test_access_via_event` had incidentally created this exact state without asserting on it.
  **Mitigation:** `ck_evnarr_duration_mode_fields` now requires at least one of `window_pre_days`/`window_post_days` non-null in bounded mode; `clean()` matches. Covered by `test_bounded_mode_with_no_window_fields_rejected_by_db_constraint` and `test_bounded_mode_with_only_post_window_set_succeeds` (the asymmetric-but-valid case).

- **Tiger 3: migration accidentally bundles unrelated pre-existing schema drift**
  **Severity:** MEDIUM
  **Likelihood:** was realized -- `makemigrations sw_events` picked up 5 unrelated `AlterField` ops on `Event`'s `SourceAwareModel`-mixin fields, confirmed present on `develop` HEAD independent of this change (`git stash` + clean-checkout `makemigrations --check --dry-run` showed identical drift with none of this PR's model edits applied).
  **Mitigation:** manually stripped the 5 unrelated ops from the generated migration (reconfirmed on a second, from-scratch regeneration after the hostile-review fixes). Flagged the drift as a follow-up ticket candidate rather than silently absorbing or silently ignoring it.

- **Tiger 4: production `db-postgis` source gets mutated by test runs**
  **Severity:** HIGH (blast radius: shared electinfo production database)
  **Likelihood:** LOW if handled correctly, but a plausible default-path mistake (Django's test settings default to `localhost`/`postgres` which could resolve to a shared resource in a different environment).
  **Mitigation:** stood up an isolated, throwaway `postgis/postgis:16-3.4` Docker container (`sw369-testpg`) never touched by anything outside this task; all `manage.py migrate`/`pytest` runs pointed `POSTGRES_HOST`/`POSTGRES_PORT` at that container explicitly via env vars, never at the workspace's `db-postgis` source. Verified via `psql`-level inspection against the container, not the production source.

- **Tiger 5: `--reuse-db` masks migration/constraint changes during iterative fixing**
  **Severity:** MEDIUM
  **Likelihood:** was realized -- this exact failure happened during the hostile-review fix cycle: `pytest --reuse-db` silently reused a `test_test_socialwarehouse` database created by Django's test runner BEFORE the constraint fixes, so two genuinely-fixed constraints appeared to still fail.
  **Mitigation:** caught via unexpected test failures against freshly-applied-migration evidence (`psql \d+` on the manually-migrated `test_socialwarehouse` DB showed the correct constraint, contradicting the test failure) -- diagnosed the DB-name mismatch (`test_socialwarehouse` vs. Django's auto-prefixed `test_test_socialwarehouse`), dropped the stale test DB, reran with `--create-db`, and confirmed 46/46 passing against the corrected schema.

- **Tiger 6: `events/admin.py` scope creep into electinfo/fec-api#545's territory**
  **Severity:** LOW
  **Likelihood:** MEDIUM (the natural instinct is to add "at least a bare admin registration" so the new model is usable at all).
  **Mitigation:** explicitly did not create `events/admin.py` in this PR; confirmed via `find` that no such file exists yet and via `gh api` that #545 is open and unstarted; noted the dependency explicitly in the PR body rather than building a throwaway registration that #545 would have to redo/conflict with.
