## Hostile Review: NarrativeEvent + EventParticipant.exposure_class (SW#369)

### Verdict: FAIL

### Findings

- **[BLOCKER]** `sourcing_note` whitespace-only bypass defeats the entire `incidental_private` protection on the standard write path
  The `clean()` override on `EventParticipant` is *stricter* than the DB `CheckConstraint`: it rejects `sourcing_note.strip() == ""` (whitespace-only), while `ck_evpart_sourcing_note_required` only rejects the literal empty string (`sourcing_note=''`). The code comment at `events.py:243-248` claims the DB constraint is what "fires on every write path, including raw `.objects.create()`" — true for the *literal-empty-string* case, but the *stricter* whitespace check lives exclusively in `clean()`, and Django's `Model.save()` (and therefore `Model.objects.create()`, which is `obj = Model(**kw); obj.save()`) never calls `clean()`/`full_clean()` automatically — this is documented, unconditional Django behavior, not project-specific. There is no `save()` override on `EventParticipant`, no signal handler, no `full_clean()` call anywhere in the app (verified via `grep -rn "full_clean\|pre_save\|post_save\|signals" socialwarehouse/events/` — zero hits).
  Concretely: `EventParticipant.objects.create(event=e, agent_uuid=..., agent_type="person", role_in_event="subject", exposure_class="incidental_private", sourcing_note="   ")` will **succeed silently** — the DB constraint sees `sourcing_note != ''` (three spaces isn't the empty string) and is satisfied; `clean()` is never invoked. This is exactly the failure mode the feature exists to prevent: an analyst (or a bulk-import script, or a bug) can name a private individual in an event with a content-free "justification" and nothing anywhere in the write path objects. The test suite gives false confidence here: `test_clean_rejects_incidental_private_with_whitespace_only_sourcing_note` only calls `p.clean()` directly on an unsaved instance — no test exercises `.objects.create()` or `.save()` with a whitespace-only note to confirm the real (buggy) behavior.
  Fix options: add the DB constraint check via `trim(sourcing_note) != ''` (Postgres `TRIM()` works fine inside a `CheckConstraint.condition` via a raw `Func`/`RawSQL`, or a generated/computed check), or override `save()` to call `full_clean()` (with the usual caveats about `save()`-triggered validation), or accept the weaker DB-only floor and delete the whitespace-only clean() check/test since it currently only protects ModelForm-mediated paths.

- **[MAJOR]** `duration_mode="bounded"` with both `window_pre_days` and `window_post_days` NULL is accepted by both the `CheckConstraint` and `clean()` — a "bounded" event with no bound
  `ck_evnarr_duration_mode_fields` clause A is `Q(duration_mode='bounded', effective_to__isnull=True)` — it says nothing about the window fields. `clean()` mirrors this exactly: for `duration_mode == "bounded"` it only checks `effective_to is not None`; it never checks that at least one (or both) window fields are set. Concretely, `NarrativeEvent.objects.create(event=e, narrative_event_type="pac_formation", duration_mode="bounded")` (no window kwargs at all) succeeds with `window_pre_days=None, window_post_days=None` — and this exact row is created (uncommented on) by the diff's own `test_access_via_event`, so the gap is already latent in the shipped test suite, just not asserted on. Given the ticket is explicitly part of a *temporal-analysis* epic (`electinfo/fec-api#543`) where `window_pre_days`/`window_post_days` presumably drive date-range queries downstream, a "bounded" `NarrativeEvent` with both fields `None` will either raise `TypeError` at `event_date - timedelta(days=None)` or be silently mishandled by whatever consumes it — the model layer provides zero defense against this operationally-meaningless state. Same gap for the asymmetric case: `duration_mode="bounded", window_pre_days=5, window_post_days=None` (only one of the two set) is also accepted by both layers; no test exercises this either.
  Recommend either requiring both window fields non-null when `duration_mode="bounded"` (mirroring the symmetry the constraint already enforces for `structural`, which requires *both* window fields null), or explicitly documenting that `None` means "use some caller-side default" and enforcing that default exists downstream — as written, it's an undocumented silent gap.

- **[MINOR]** Migration's `CreateModel(NarrativeEvent)` / `AddField(narrativeevent, event, ...)` split deviates from every sibling subtype's migration shape, and I could not confirm live that it's what a clean `makemigrations` run actually produces
  `CorporateEvent`, `SpatioTemporalEvent`, and `ElectoralEvent` all include their `event` `OneToOneField` directly inside a single `CreateModel(...)` op in `0001_initial.py`. This migration instead creates `NarrativeEvent` *without* the `event` field, then adds `event` via a separate `AddField` several operations later (after the `EventParticipant` field/constraint ops and the `Event.event_type` `AlterField`). Functionally this is harmless as a sequence of DDL (empty table at `AddField` time, `AddIndex`/`AddConstraint` for `NarrativeEvent` reference only columns already present after `CreateModel`), and I manually cross-referenced every field, index, and constraint in this migration against the current `NarrativeEvent`/`EventParticipant` model definitions field-by-field and found no completeness gap for the fields *this PR* introduces. But the *shape* of the split is atypical enough (and hand-editing is exactly the kind of process that could produce an artifact like this) that I'd want the author to paste the output of a truly clean-tree `makemigrations --check --dry-run` confirming this exact operation ordering is what Django's autodetector natively produces, not a side effect of removing the 5 unrelated ops. I attempted to verify this myself (`manage.py makemigrations --check --dry-run` against the migrated test DB) but every `python`/`git`/`manage.py` invocation in this session was blocked by an unrelated `universal-mutation-gate` hook whose `think-gate.json` state references a stale ticket (`electinfo/enterprise#2791`) from a prior task in this same workspace — plain `cat`/`grep`/`find` reads were unaffected, so this finding is based on static cross-referencing only, not live execution.
  Separately, I *did* confirm (via `Read` of `socialwarehouse/core/mixins.py` vs `0001_initial.py`/`0002_event_canonicalization.py`) that the 5 stripped `AlterField` ops (`data_source`/`jurisdiction_level`/`jurisdiction_state`/`source_record_id`/`ingested_at`) correspond exactly to `help_text=` strings present on `SourceAwareModel` in current `mixins.py` that are absent from both prior migrations — this is real, pre-existing, cosmetic-only drift (`help_text` has no DB-level representation, so no DDL/data risk from omitting it), unrelated to this PR. Stripping those 5 ops was safe. I'd still recommend a follow-up ticket to capture that drift in its own migration so it stops reappearing in every future `makemigrations --check`.

- **[MINOR]** Inconsistent `ValidationError` shape within `NarrativeEvent.clean()`
  The bounded-mode branch raises a field-keyed error: `ValidationError({"effective_to": "..."})`. The structural-mode branch raises a bare string: `ValidationError("window_pre_days/window_post_days only apply in bounded mode.")`, which Django treats as a non-field (`__all__`/`NON_FIELD_ERRORS`) error rather than attaching it to `window_pre_days`/`window_post_days`. In a `ModelForm` context this means the effective_to error renders next to its field while the window-fields error renders as a generic form-level error — inconsistent within the same method for a structurally symmetric pair of checks.

- **[MINOR]** No enforcement that `Event.event_type` matches the attached subtype (`NarrativeEvent`, or any sibling)
  Nothing prevents `NarrativeEvent.objects.create(event=<an Event with event_type="transaction">, ...)`. This is a pre-existing gap shared by `CorporateEvent`/`SpatioTemporalEvent`/`ElectoralEvent` (none of them tie back to `Event.event_type` via a constraint either), so it's not a regression introduced by this PR — but this PR is the one that establishes the "use a `CheckConstraint` for cross-field invariants" house style within this file, which makes the omission more conspicuous here. Worth a follow-up ticket rather than a blocker on this PR.

- **[MINOR]** Test coverage gaps
  (a) No test exercises `.objects.create()`/`.save()` (as opposed to calling `.clean()` directly) with a whitespace-only `sourcing_note` to prove the real (buggy) runtime behavior described in the BLOCKER finding above — the existing whitespace test only proves `clean()` itself works when called directly, which nothing in the write path actually does.
  (b) No test for `duration_mode="bounded"` with null or partial window fields (see MAJOR finding above) — `test_access_via_event` incidentally creates exactly this state but doesn't assert on it.
  (c) No test exercises the UPDATE path: re-saving an existing `public_actor` participant with `exposure_class="incidental_private"` and an empty/unchanged `sourcing_note` to confirm the DB constraint re-validates on `UPDATE`, not just `INSERT`. (I traced through the Postgres semantics and Django's `AddField(default=...)`-then-`AddConstraint` ordering by hand — the constraint will correctly fire on `UPDATE` too, and existing rows are safe at migration-apply time because the field defaults land before the constraint is added — but this is untested.)
  (d) No test for `Event.event_type` / subtype mismatch (see prior finding).

### What was verified

- Traced `ck_evnarr_duration_mode_fields`'s SQL (`(duration_mode='bounded' AND effective_to IS NULL) OR (duration_mode='structural' AND window_pre_days IS NULL AND window_post_days IS NULL)`) against all combinations of `duration_mode x {both-window-null, one-window-set, both-window-set} x {effective_to null/set}` by hand; confirmed it correctly rejects `bounded+effective_to-set` and `structural+any-window-set`, correctly accepts `structural` regardless of `effective_to`, but does **not** require any window field to be set for `bounded` (MAJOR finding above).
- Traced `ck_evpart_sourcing_note_required`'s SQL (`NOT (exposure_class='incidental_private' AND sourcing_note='')`) and confirmed it only catches the literal empty string, not whitespace (BLOCKER finding above).
- Checked Postgres three-valued (NULL/UNKNOWN) `CHECK` constraint semantics against both constraints specifically: confirmed neither constraint's equality comparisons (`duration_mode=...`, `exposure_class=...`, `sourcing_note=''`) touch a nullable column (`duration_mode`, `exposure_class`, `sourcing_note` are all `null=False` in the model), and the only nullable columns referenced (`effective_to`, `window_pre_days`, `window_post_days`) are only ever compared via `__isnull`, which is always boolean-determinate. No NULL-vs-UNKNOWN gotcha applies to either constraint.
- Confirmed via `grep -rn "full_clean\|pre_save\|post_save\|signals"` across `socialwarehouse/events/` that nothing calls `full_clean()`/`clean()` automatically anywhere in the write path, and confirmed `EventParticipant` has no custom `save()` override (only `Event.save()` is overridden, and only to derive `year`).
- Manually cross-referenced every field, `Meta.indexes` entry, and `Meta.constraints` entry of `NarrativeEvent` and the two new `EventParticipant` fields against the migration's operations, field-by-field, and found the migration IS complete for everything this PR's models require (no missing field/index/constraint specific to the new code).
- Confirmed via `Read` comparison of `socialwarehouse/core/mixins.py` (`SourceAwareModel`) against `0001_initial.py`/`0002_event_canonicalization.py` that the 5 stripped `AlterField` ops correspond exactly to `help_text=` additions with no DB-schema representation — genuine pre-existing, unrelated, DDL-inert drift, safe to strip.
- Confirmed the `AddConstraint(eventparticipant, ck_evpart_sourcing_note_required)` op is correctly ordered after both new-field `AddField` ops (required, since the constraint references both new columns) and confirmed it's safe against pre-existing `EventParticipant` rows because those rows get backfilled with `exposure_class="public_actor"` (the field default) before the constraint is added in the same migration.
