## Hostile Review: EventLink (SW#370)

### Verdict: PASS WITH NOTES

### Findings

- **[MINOR, FIXED]** No test proves CHECK constraints re-fire on UPDATE, not just INSERT
  All DB-level tests only exercised `EventLink.objects.create(...)`, i.e. the INSERT path. There was no test creating a valid `EventLink` and then mutating it in place to prove the constraint re-fires on UPDATE. Manually verified via a live-DB probe (rolled back) that Postgres CHECK constraints DO correctly re-fire on UPDATE. No live bug, but the suite didn't lock this in. **Fixed**: added `test_self_loop_via_update_rejected_by_db_constraint`.

- **[MINOR, FIXED]** One-to-many was only tested in the source-to-target(s) direction
  `test_one_to_many_kennedy_obama_worked_example` proved one `source_event` can link to three different `target_event`s, but there was no test proving the reverse shape -- multiple different `source_event`s linking to the same `target_event`. `unique_together` is scoped to the full `(source_event, target_event, edge_type)` triple so nothing structurally prevents this, confirmed via manual probe. **Fixed**: added `test_many_to_one_multiple_sources_link_to_same_target`.

- **[MINOR, NOT FIXED]** DB-level IntegrityError tests don't assert *which* constraint fired
  All constraint-violation tests use bare `pytest.raises(IntegrityError)` without inspecting `str(exc.value)` for the specific constraint name. Manually verified (via live-DB probes) that today each scenario is attributable to exactly the intended constraint with no other constraint capable of producing a false-positive `IntegrityError` on that same input -- not presently masking anything, but a latent risk if a future constraint's condition overlaps a test fixture. Not fixed: this matches the existing precedent from SW#369's own `EventParticipant` tests, which also use bare `IntegrityError` assertions without constraint-name inspection -- consistent with established repo convention, not a regression.

- **[MINOR / informational, NOT FIXED]** Index redundancy on `source_event_id` / `target_event_id` / `edge_type`
  The schema has both automatic single-column FK/db_index indexes and the explicit composite indexes (`idx_evlink_source_type` / `idx_evlink_target_type`), which overlap. Confirmed this identical redundancy pattern already exists on the sibling `sw_event_participant` table -- this PR is following established repo convention, not introducing a new problem. Not fixed; flagged for awareness only.

This is the exact pattern documented in Django's own docs for cross-field CheckConstraints; no F()/Q() resolution bug.
  - `ck_evlink_edge_type_valid` compiles to `CHECK (((edge_type)::text = ANY (ARRAY['precedes','relates_to']::text[])))`.
